# Self-service SonarQube migration

Automation for migrating SonarQube projects from entity SonarQube
instances to the group's central instance, preserving analysis history.
The source project team triggers the request itself, once its
application's DevOps space has been created on the portal.

The hard part: nothing in the target key generated by the DevOps portal
makes it possible to recover the source key. It is the requester who
declares the `(source key, target key)` pair, and the entire security of
the solution rests on verifying that pair — see
`sonar-migration-engine/src/migration/` for the authorization check, the
core of the mechanism.

## Structure of this repository

This monorepo hosts, **for development purposes**, the three repositories
that will be split into three distinct GitLab projects at deployment time
(see [`scripts/split-repos.sh`](scripts/split-repos.sh)). They have
different permissions in the final product: developing them side by side
here avoids having to synchronize three repositories while writing and
testing, without changing any of the security guarantees, which are
grounded in the three *final* repositories, not this one.

| Repository | Content | Project team permissions | Protected variables |
|---|---|---|---|
| [`sonar-migration-engine/`](sonar-migration-engine/) | The `.gitlab-ci.yml` actually executed, Ansible roles, authorization check, instance inventory | **None** | Yes, all the tokens |
| [`sonar-migration-requests/`](sonar-migration-requests/) | Migration requests, public catalogue of instances | Developer | No |
| [`sonar-migration-runs/`](sonar-migration-runs/) | Append-only execution journal, reports, authorization proofs | Read-only | No |

## Installation

Deploying this solution for the first time (creating the three GitLab

## The setting that protects everything else: CI configuration path

This is the only setting that neutralizes the "I modify the pipeline in
my own merge request" threat: without it, none of the guarantees below
hold, regardless of code quality. **To do before any deployment, on the
GitLab project `sonar-migration-requests`:**

1. Open `sonar-migration-requests` → **Settings → CI/CD**.
2. Expand the **General pipelines** section.
3. In the **CI/CD configuration file** field, enter the path of the
   pipeline file hosted in the engine repository, in the form:
   ```
   ci/pipeline.yml@<group>/sonar-migration-engine
   ```
   (the `ci/pipeline.yml` file was delivered in batch 3; the exact path
   is to be confirmed at deployment time).
4. **Save.**
5. Check that the [`sonar-migration-requests/.gitlab-ci.yml`](sonar-migration-requests/.gitlab-ci.yml)
   file present in this repository stays inert: its content will
   **never be read** once this setting is active, even if modified in
   the same merge request as a request. This is deliberate — see the
   comment at the top of that file.
6. Check, under **Settings → Repository → Protected branches**, that
   `main` is push-protected for everyone except the central team, and
   that Developer can only propose merge requests.

Without this setting, a contributor to the requests repository could, in
the same MR as their request, add a job that bypasses the authorization
check. With this setting, the requests repository's `.gitlab-ci.yml` is a
dead file.

## Splitting into distinct GitLab repositories

See [`scripts/split-repos.sh`](scripts/split-repos.sh): a commented
script that extracts each of the three folders into its own GitLab
repository via `git subtree split`, preserving history.

## Sequence, authorization check, state machine

The full technical detail (authorization check algorithm, thirteen-step
sequence, state machine, GitLab CI / Ansible split) is that of the design
document validated upstream; this monorepo implements it batch by batch:

- **Batch 1** — delivered: structure of the three repositories, request
  input contract, instance inventory.
- **Batch 2** — delivered: the authorization check (Python module + unit
  tests).
- **Batch 3** — delivered: the GitLab CI pipeline (`ci/pipeline.yml`), the
  state machine (`machine_etats.py`), the journal (`journal.py`), MR
  comment rendering (`rapport.py`, `notification.py`).
- **Batch 4** — delivered: the Ansible roles (`ansible/roles/`) —
  preflight, export, transfer, capture, deletion, placeholder, import,
  rename, configuration reapplication —, the multi-entity dynamic
  inventory (`ansible/inventaire/depuis_instances.py`), Compute Engine
  task tracking (`ansible/docs/suivi_taches_ce.md`).
- **Batch 5** — delivered: the operations runbook
  (`sonar-migration-engine/docs/runbook.md`), the audit logging contract
  (`sonar-migration-runs/README.md`), metrics
  (`sonar-migration-engine/src/migration/metriques.py`,
  `python -m migration.cli metriques`).
- **Batch 6** — delivered: the pilot project validation plan
  (`sonar-migration-engine/docs/plan-validation-pilotes.md`), covering
  the prompt's six refused-authorization cases and a full end-to-end
  migration.

The six batches requested by the prompt have been delivered.
