# Migrating your project — a guide for project teams

This walks a project team through migrating one SonarQube project from
your entity's instance to the group's central instance, with analysis
history preserved. If you just need the short version, see the root
[`README.md`](../README.md) of this repository; this document goes
further, with the exact field formats, what each step actually checks,
and what every refusal message means for you.

## Who this is for

Anyone on the project team who is (or can become) an **administrator of
the project on both instances**: the source project on your entity's
SonarQube, and the target project on the central instance. That dual
administration is the entire security model of this migration (see the
root monorepo README if you're curious why) — there is no other approval
path, and no one can submit this request on your behalf without also
meeting that condition.

## Before you start — a four-point checklist

1. **Your DevOps space and its SonarQube project already exist**,
   created through the **DevOps portal**. This is what generates your
   target key and the `sonar-<space_id>-managers` group that makes you an
   administrator of the target project. Skip this and your request is
   refused immediately with `PROJET_CIBLE_INCONNU` — there is nothing to
   migrate into yet.
2. **Your entity's instance is onboarded.** Check
   [`docs/instances-disponibles.md`](instances-disponibles.md) for its
   identifier. Not listed? Contact the central team before doing anything
   else — submitting a request for an unlisted instance is refused with
   `INSTANCE_INCONNUE`.
3. **You are an administrator of the source project**, on your entity's
   instance — directly, or through a group you belong to.
4. **You have signed in at least once, on both instances**, through the
   corporate SSO. Identity resolution depends on your account already
   existing there; an account that has never logged in is invisible to
   the check (`COMPTE_INCONNU_INSTANCE`).

## What actually happens, end to end

```
you: open a merge request
        │
        ▼
automated check (minutes)  →  comment on your MR: passed or refused
        │ passed
        ▼
central team schedules and runs the migration
 (a window agreed with you — not immediate, not self-service)
        │
        ▼
final report posted as a comment on your MR
```

Two separate comments land on your merge request, at two different
times: the **authorization verdict** (fast, automatic, no server-side
action taken yet) and the **final report** (after the actual migration,
which the central team triggers manually within an agreed window). A
passed authorization check is not a completed migration — nothing has
moved yet at that point.

## Step by step: submitting your request

**1. Find your instance identifier and the file layout.**
Look up your entity in
[`docs/instances-disponibles.md`](instances-disponibles.md) — that
identifier is your `instance_source` and your folder name.

**2. Create a branch, then duplicate the template:**
```
requests/entite-exemple/grp-exemple-facturation-api.yml
  → requests/<your instance identifier>/<your target key>.yml
```
The file name must be your **target key** (the one from the portal),
with `.yml` — not a project name, not a ticket number. A mismatch between
the folder/file name and the fields inside is refused
(`CHEMIN_DOSSIER_INCOHERENT` / `CHEMIN_NOM_FICHIER_INCOHERENT`) before
anything else is even checked.

**3. Fill in the fields:**

| Field | Required | Format | Example | Notes |
|---|---|---|---|---|
| `version` | yes | must be `1` | `1` | Fixed — do not change. |
| `instance_source` | yes | lowercase letters/digits/dashes, 2-32 chars | `entite-alpha` | From `docs/instances-disponibles.md`. |
| `cle_source` | yes | letters, digits, `_` `.` `:` `-`, 1-400 chars | `com.alpha:facturation-api` | The project's **current** key on your entity's instance. |
| `cle_cible` | yes | same charset as above | `grp-alpha-facturation-api` | The key generated by the DevOps portal — copy it exactly, do not invent one. |
| `ticket` | no | `ABC-123`-style reference | `DEVOPS-4821` | Copied into the report only, never used in any decision. |
| `fenetre_souhaitee` | no | `YYYY-MM-DD` | `2026-09-15` | Indicative — the central team confirms the real window with you separately. |
| `commentaire` | no | free text, ≤ 500 characters | — | Context for the central team; never interpolated into anything. |

`cle_source` and `cle_cible` must be **different** — the migration
deletes whatever currently holds the target key before importing your
history, so identical keys would delete the very project you're
migrating (`CLES_IDENTIQUES`).

**4. Open a merge request to `main`**, using the provided template — it
already lists the same checklist as above.

**5. Wait for the first comment before doing anything else.** Do not
merge again, do not force-push a "fixed" version hoping it re-triggers
faster, do not open a second MR for the same key while the first is
pending — see "One request, one file, once" below.

## Reading the automated check's comment

**On success**, the comment confirms both sides passed and states that no
action has been taken yet — the actual migration is a separate, later
step (see above).

**On refusal**, the comment lists, for **each** side (source and target)
independently, whether it passed and why not — you always see the state
of both, not just "denied." Below that, a "What to do" section gives one
action per refusal code. The wording in your MR comment is always the
authoritative one — it comes from
[`messages.py`](../../sonar-migration-engine/src/migration/messages.py)
in the engine repository; the table below is a quick reference, grouped
by who needs to act, not a copy to rely on if it ever drifts.

**You can fix these yourself, then resubmit as a new request:**

| Code | What it means |
|---|---|
| `PAS_ADMIN` | You're not an administrator of that project (directly or via a group) on that instance. |
| `COMPTE_INCONNU_INSTANCE` | Your account has never logged into that instance — sign in once via SSO, then resubmit. |
| `PROJET_SOURCE_INCONNU` | The source key doesn't match any project on the source instance — check for a typo. |
| `PROJET_CIBLE_INCONNU` | The target key doesn't match any project on the central instance — the DevOps portal step (checklist point 1) probably wasn't done yet. |
| `CLES_IDENTIQUES` | Source and target keys are the same — check the key the portal actually generated. |
| `INSTANCE_INCONNUE` | `instance_source` doesn't match anything published — check the spelling against `docs/instances-disponibles.md`. |
| `DOUBLON_COUPLE_SOURCE` | Your source project is already claimed by another request file — remove the obsolete one. |
| `FICHIER_*`, `SCHEMA_*`, `YAML_*`, `CHEMIN_*` codes | A problem with the file itself — missing, too large, wrong location, invalid YAML, or a field that doesn't match the contract. The message always names the exact field or issue. |

**These need the central team — contact them rather than retrying:**

| Code | What it means |
|---|---|
| `INSTANCE_INACTIVE` | Your instance is onboarded but not currently accepting migrations. |
| `PROJET_CIBLE_SANS_GROUPE_ADMIN` | The target project exists but its provisioning looks incomplete. |
| `PROJET_CIBLE_DEJA_ANALYSE` | The target project already has analyses — importing would overwrite data. |
| `DOUBLON_ANNUAIRE` | Your directory identifier matches more than one local account — a directory anomaly, not something you can fix. |
| `DOUBLON_CLE_CIBLE` | Your target key is already claimed by another request — only relevant if you believe that earlier one failed. |
| `SLUG_COLLISION`, `CLE_SOURCE_COLLISION_CENTRALE` | Naming collisions that need a decision above the automated check. |

**One more thing you might see even on a passing check**: a section
titled "Flagged for the central team" (e.g. `GROUPE_TROP_LARGE`, an admin
group considered too broad to count toward authorization). This does
**not** block your request as long as a legitimate authorization path
still exists elsewhere — it's the central team's problem to clean up, not
something that stops your migration or needs any action from you.

## If your request is accepted

Nothing happens automatically beyond the check itself. The central team
schedules the actual migration and runs it manually, within a window
agreed with you separately (not necessarily right away) — you'll see a
**second**, distinct comment (the final report) once it's done or if it
had to stop partway.

**On completion**, the report confirms the migration is done and reminds
you of the one thing that is genuinely on you: the migration moves your
analysis history to the new key, but it **does not touch your code
repositories**. Point your analyses
(`sonar-project.properties`, your CI configuration) at the new target key
yourself, after the report confirms success — not before, and not
automatically.

**If it's interrupted partway**, the report states the last confirmed
step and explicitly says no action is needed on your side — the central
team handles recovery. Do not attempt to "help" by resubmitting a new
request for the same pair while this is unresolved (see below).

## One request, one file, once

A given `(source instance, source key)` pair and a given target key can
each be migrated **successfully only once** — the journal refuses a
repeat. If you're unsure whether an earlier request of yours actually
succeeded, ask the central team rather than opening a second request "just
in case": a genuine duplicate is refused with `DOUBLON_CLE_CIBLE` /
`DOUBLON_COUPLE_SOURCE`, but if something is actually stuck, resubmitting
doesn't help and just adds noise.

## What you cannot do from this repository

This repository's own `.gitlab-ci.yml` is never executed — see the
comment at the top of that file. Modifying anything other than your one
request file in your merge request has no effect on the pipeline: it
isn't read from here regardless of what the MR contains.
